Elaspic is web application which displays a gallery of the photos the user has previously uploaded
to it. The UI is consists in 3 screens
- login: the page ask for the username and stores it during the whole session
- gallery: here the user can see the pictures in a grid. Images are a lighter version so there is less bytes to load (thumbnails)
- detail: here the use can see the original image. he also can add tags and put comment that will be linked to his username.

## Structure of the application

The application is split into 2 services.

### API Service

The API is a nodejs application that is built on top of the express framework. I provides some endpoints for user
registration and authentifcation and some RESTful URLs for clients to consume.

- /register: this endpoint that only accepts POST requrest and its goal is to register new users into the system.
for the register to work it requires a username, a valid email and a password. these fields should be validated:
- username: required and unique in the system. only alphanumerical chars and "_" are accepted.
- email: required and unique in the system. must be a valid email
- password: required. any letter, number or special chars and min lenght should be 10

Validation errors in format like password too short should be returned explicitly explaining what is failing. Example:
```json
{
  "message": "Validation error",
  "errors": [
    { "field": "username", "message": "the username field contains invalid chars" },
    { "field": "email", "message": "the email field contains s not an email" },
    { "field": "password", "message": "the password field is too short" },
  ]
}
```
but do not disclose if a user or email is already in the system. Instead return a generic error.
```json
{
  "message": "userame or email already registered"
}
```
If the registration is successfull a new user is created wiht the following information
- username: the username provided in the registration
- email: the email provided in the registration
- salt: a random string generated by the system. it will be used to hash the password
- password: contains the hash result of (password + salt). the hash algorithm should be slow to avoid brute force attacks (like bcrypt)

- /login: this endpoint does the login funciton. accepts only POST request and validates username & password returning
a token if correct. this token will be used later to validate the client has authenticated. Similar to register
show explicit errors in field validations but if the format is correct but if the validation with the DB failed return
```json
{
  "message": "invalid userame or password"
}
```
The process of validation the login is:
- query for the password and salt for the given username. if not foind fail with the invalide username message above
- run the hash algorithm with (request password + salt)
- compare the hash with the password in the database if
  - equal login is complete and returns a token and sets an http only cookie for authentication
  - different fail with the invalid user/password message

NOTE: only register and login endpoints can have anonymous request. the others should provide a valid token in the headers. the system also will check the presence of the http only cookie

- /pics: this is the resource to manage pictures for the current user and it follows the classic REST rules. The user 
is in the context of the request thanks to the token returned un the /login.
A simple get request returns a list, "/pics/:id" returns the picture with the given id or a 404 if not exists,
post to "/pics" will save a new picture into the database and a delete to "/pics/:id" will remove the picture.

- /pics/:id/comments: this will be REST enpoint for comments related to the pics. The comments will keep a reference of the user
that did it.

- /users: for this resource it will only allow to list users (GET request) that have been already registered. The user model contains only the username and id. the is is a uuid generated at the moment of creation.

- /users/{userId}/pics: resource of the pictures of another user in the system. The GET request returns the pic uploaded by
the username with the {userId}. It is not allowed to POST,PUT,DELETE a pic of nother user so this acitons are not implemented.

- /users/{id}/pics/{picId}/comments: rest endpoint for the comments of a picture from another user in the system.
GET will return al the comments but the current user is only allowed to:
- POST a new comment
- PUT (edit) a comment he authored. He cannot modify comments from others
- DELETE a comment he authored. He cannot delete comment from others. It's a logical delete and it won't be removed form the DB


### Data Model

The API handles different data models for: users, pictures, comments. Some generic rules:
- ID fields are UUIDv4 strings. We will make use of `crypto.randomUUID` to generate them

the data model for users is
```json
{
  id: "__UUID__",                   // UUIDv4 following the generic rules
  username: "username",             // the username set on registration
  email: "user@elastic.co",         // the email set on registration
  salt: "_random_string_",          // salt for hashing. randomly generated and long (30 chars min)
  password: "hash(password+salt)",  // result of the hash function with password and salt concatenation
  createdAt: "2026-11-11T00:00:01"  // Date in ISO string format
}
```

the data model for pictures is
```json
{
  id: "__UUID__",                   // UUIDv4 following the generic rules
  author: "_username_",             // the username of the author of the picture, set when uploaded
  base64: "data:png;base64,AAA",    // the image content in base64
  createdAt: "2026-11-11T00:00:01"  // Date in ISO string format
}
```


the data model for comments is
```json
{
  id: "__UUID__",                   // and UUID v4 string. probably generated by nodejs crypto.randomUUID
  author: "_username_",             // the username of the author of the comment
  picture: "picId",                 // the ID of the picture where the comment was created
  comment: "hello",                 // the actual comment string or null if deleted
  deleted: false,                   // boolean that indicates if the commant was deleted
  createdAt: "2026-11-11T00:00:01"  // Date in ISO string format
}
```


### The UI Service

This is Reactjs application that works in single page application mode. For styling and
layout its using Elastic's desing system. Documentation can be found in https://eui.elastic.co/

#### UI Architecture

The UI service is developed by different teams and each one of them is responsible of one of the routes available in the app.
For better organization it was decided that each team will own a micro frontend that will be mounted by a shell application.
Micro frontends are Reactjs component that will be loaded dynamically by the router.
The shell application is a Reactjs component that has:
- a header and a sidebar that will be hidden in login and registration and shown when user logged in
- a router that has default route the login. changing a route means loading a micr forntend 

Below its the description of each route/micro frontend

- "/login": login route is handled by the "login" micro frontend and shows a login form asking only for the username and password. Validation of format should be done before posting the data (matching backend format validations). IMPORTANT: if the user is not set (not logged in) the other routes must redirect to this one.
The login form must show a link to the regitration form for users who want to join.

- "/register": register route is handled by the "Register" micro frontend and shows a registration form where it asks for username, password and email. All required and format validation should be done before
posting data to the register endpoint.

The rest of the routes require the user to be authenticated. This means to have a token returned by the login endpoint of the API. any hit on these routes without being authenticated gets a redirect to /login route. Once authenticated the shell will display
- the hader component with
  - elastic logo on the right side. if clicked it goes to "/pics" route
  - the username and a logout button on the top left
- a sidebar component with two links (each one with an icon)
  - to "/pics" route
  - to "/users" route

- "/pics": all routes with this prefix will be handled by the "Pictures" micro frontend
  - this route will mount the "Pics" micro frontend. it will display a grid with all the pictures uploaded by the current user.
  - clicking on a picture it will navigate to "/pics/{picId}".
  - "/pics/{picId}" it will display a detail view the picture and on the side it will show a list of the comments made by himseld and other users. comments will be sorted by date descending. each comment will display the username of the author
  - user can make a comment to the picture. and delete the ones he made previously
  - the user will be able to navigate back to the grid of pictures

- "/users": all routes with this prefix will be handled by the "Users" micro frontend
  - this route will mount the "USers" micro frontend. it will display a list of the resitered users. clicking a username i will go to the "/user/{username}" route
  - "/users/{username}" route will dsplay a grid of pictures uploaded bt the user with the username set on the route. if the username does not exist it should return to the "/users" route.
  - clicking on a picture it will navigate to "/users/{username}/{picId}". it will display a detail view the picture and on the side it will show a list of the comments.
  - user can make a comment to the picture. and delete the ones he made previously
  - the user will be able to navigate back


## Global Architecture

A part from the services described above the system has other components that are necessary to work.
For now we want to spin up the whole system with a docker compose file.

The services in the compose are:

- database service: a mysql database that can be accessed through docker internal network
- api service: the nodejs express api defined before. depends on the database to work
- ui service: also defined before. depends on the api service to work
- nginx proxy: the only component available to the outside world. its responsibility is to redirect request to the right place
  - request with url pathname starting with "/api/" will go to the api service
  - request with url pathname starting with "/collect/" will forward to an external server
    - the target host will be set on the docker compose with env var named `OTEL_EXPORTER_OTLP_ENDPOINT`
    - an ApiKey will be set on the docker compose file with env var named `ELASTIC_OTEL_API_KEY`
    - the forwarded request will add an authorization header with the value of `ELASTIC_OTEL_API_KEY`
    - host, x-forwarded-for and x-real-ip headers are also set
  - other requests will go to the UI service
